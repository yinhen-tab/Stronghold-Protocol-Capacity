## 35. 0.3.2

This branch (`integrate/capacity-20p`) carries three sets of changes on top of 0.3.1: wearable picture-only
outfits lifted from upstream 0.3.2 (§35.4), the 20-player capacity layer (§35.5) and the operations layer (§35.6).
Upstream 0.3.2's §35.1 (settlement layout, #745), §35.2 (local extractor Python guard, #744) and §35.3 (bond timers,
issue #746) are **not** part of this branch; the numbering is kept so that the links to §35.4 in DESIGN.md, SKINS.md
and design/client.md resolve.

### 35.4 Picture-only outfits (B6)

- **Seen:** the 0.3.1 known issue excluded outfits with avatars / portraits but no Spine, including Forge skin-catalogue
  outfits already imported into the skins layer. Cards and panels also continued reading the default pictures.
- **Official / decision:** the maintainer chose option A on 2026-10-18: those outfits become wearable, labelled
  「仅更换头像与立绘」, with the default battle model and independent missing-picture fallbacks. The official
  [skin_table.json](https://raw.githubusercontent.com/Kengxxiao/ArknightsGameData/master/zh_CN/gamedata/excel/skin_table.json)
  `charSkins` separates `skinId`, `charId`, `avatarId`, `portraitId`, `illustId` and `battleSkin` (for example
  `char_285_medic2#1`). Local `activity_table.activity.AUTOCHESS_SEASON.act2autochess.charShopChessDatas`
  `chess_char_3_01_a` still maps `char_103_angel` to `backupCharId: char_603_csnipe`. Missing plugin models are a
  remake presentation policy, not an official gameplay rule.
- **Cause:** `availableSkins().playable` required `skinHasModel`, and the picker filtered out everything else.
  DOM card URL helpers never received an owner's selection; result and foreign-detail paths dropped the owner.
- **Now:** a model or pictures enables an outfit; the global picker gate stays global. `OperatorImage` and the pure
  URL helpers apply each owner's public choice to cards, details, bond members and result pictures; the local picker
  uses its own saved choices. Stand-ins / DIY resolve their effective body first. Open images follow choice, visibility
  and manifest changes; public clears beat stale unit metadata. The combat meter retains effective-body picture
  metadata; the DOM fallback field accepts the same seat / choice updates. Spine resolution retains default Front / Back for picture-only skins and skin models for model
  outfits. No wire, importer, simulation or generated-data changes. Normative updates: SKINS.md, PLUGINS.md §9,
  design/client.md §9, DESIGN index and PLAYING.md; the previous model-only limitation is removed.
- **[ASSUMED]:** the existing E2 and illustration fields count as pictures, while metadata alone does not. An unfinished Spine
  map without Front uses both default views. E2-only art replaces only elite images in play. Picture fields keep the existing normal / elite fallback order; portrait
  may use the outfit's illustration, avatars never do. Card updates follow the renderer's latest public map (including
  clears), then unit metadata if the owner is unavailable; they never borrow the viewer's choice for another seat.
  Unowned catalogue / studio comparison / historical statistics images retain defaults. These choices do not alter gameplay.
- **Tests:** `test/ui/picture-skins.test.js` covers picker eligibility, two owners / spectators / visibility / clears,
  individual image fallbacks, normal / elite art, default Front / Back and model outfits, effective stand-in / DIY
  bodies and owner propagation through cards / details / results. `test/match/combat-metrics.test.js` adds
  effective-body / elite picture metadata coverage. Updated picker and stand-in UI tests retain prior behavior. `SP_E2E=1 node --test test/ui/picture-skins.e2e.test.js` mounts the production picker, shop card and avatar
  with original synthetic PNGs and checks note layout (desktop / landscape phone), selection, persistence, distinct
  seats, public changes / clears, visibility off/on and plugin removal.
  Browser execution is left to the reviewer because Chrome is unavailable in this sandbox. Golden scenarios unchanged.

### 35.5 The 20-player capacity layer

- **Seen:** the upstream engine tops out at a single shared card pool and serial drafting, so a room larger than the
  original four-seat design spreads each operator across every seat. The `feat/IncreasePlayerCapacity` branch
  (based on upstream v0.2.4) had solved this; 0.3.1 never carried it.
- **Official / decision:** seat capacity 4 / 8 / 10 / 16 / 20 (default 8, hard cap 20); the pool and the drafting
  groups are frozen by the seat count at match start and never re-grouped on elimination. Groups of five scale the
  complete co-op pool by 1.25 (tier III floors to 45); groups of three and four use it whole. Owned copies (sold,
  merged, eliminated) circulate inside the owner's group only. Every group drafts in parallel with independent
  six-card pages; all groups finish before the phase advances. AI alignment soft-avoids the alive teammates of its
  **own** group only. Per-group timers: 50 s per drafting round, 30 s for the first group page and 16 s after.
  Normative text: [PLAYER_CAPACITY.md](../PLAYER_CAPACITY.md); decisions D010, D012, D028, D029, D034, D035.
- **Carried over from 0.3.1 unchanged:** the shared-stock debt model (#624 / D034) for displayed operator cards, the
  private 自选 stock, and the fixed-gift identities — including the upstream `noPool` marker that lets a granted fixed
  item upgrade or merge after its group's stock is exhausted (§35.5.1).
- **Now:** `server/match/pool.js` builds one `SharedPool` and one `SharedItemPool` per fixed group
  (`createPoolGroups`); `m.pool` / `m.itemPool` remain the first group as a compatibility alias, while every rule path
  resolves through `playerPools` / `itemPoolFor(player)`. `server/match/invariants.js` and `test/match/harness.js`
  conserve each group separately — a balanced global total alone would hide a cross-group return bug.
- **Self-picked stock:** the private 自选 stock doubles in co-op like the shared pool (GitHub #650, the maintainer's
  decision of 2026-10-15, upstream 0.3.0): tier V is 16 copies and tier VI 10, solo still 8 / 5. It does not take the
  1.25 five-player scale, which belongs to the shared group pool.
- **Tests:** `test/match/player-capacity.test.js`, `lobby-capacity`, `draft-capacity`, `unite-capacity`,
  `sell-capacity`, `group-drafts`, `group-draft-generation`, `poolGroups`, `group-unite-rounds` and
  `upstream-v026-capacity`. Golden scenarios unchanged: the capacity rules only act from three seats up.

#### 35.5.1 The fixed gift's `noPool` marker

- **Seen:** 0.3.1 expressed a fixed gift's stock exemption with an internal `unlimitedGift` flag only; the piece
  itself carried nothing, so a later upgrade or merge could not inherit the identity.
- **Official / decision:** [D034](../development/DECISIONS.md#d034) says the fixed gift's upgrade and merge identity
  follow the existing rules **combined with the upstream fix**. Both are kept, not one instead of the other.
- **Now:** `acquireItem` accepts `noPool` and marks the piece; the exemption predicate is
  `(noPool === true || requirePool === false) && isUnlimitedGiftItem(itemId)`, so an ordinary item still cannot bypass
  its own group's stock by asking for either flag. `upgradeItem` exempts a marked fixed item from the exhaustion
  check, and `_mergeItem` gives the merged piece the marker when every consumed piece carried it.
  `held()` deliberately still counts those pieces, so the stock figures stay honest.

### 35.6 The operations layer

- **Seen:** 0.3.1 shipped the operations modules but never wired them into the boot path: no announcements, no asset
  cache mount, no bandwidth emergency, no persisted owner settings, and no public room directory over HTTP.
- **Now, wired in `server/index.js` and `server/http/routes.js`:**
  - announcements — `runtime/` Markdown, `GET /api/announcements`, `GET /api/announcements/<id>` and a dedicated
    picture mount; notice commands push a new article to the connected players ([ANNOUNCEMENTS.md](../ANNOUNCEMENTS.md)).
  - the asset cache — `/api/asset-cache/` (`status`, `catalog`, `catalog-update`, `file`), with owner-set limits, an
    admission summary, and an optional requirement that a client finish caching before it may join
    ([ASSET_CACHE.md](../ASSET_CACHE.md)).
  - the bandwidth emergency — `503` + `Retry-After` for ordinary requests while it protects the server, WebSocket
    sessions frozen rather than dropped, automatic resume once congestion clears.
  - persisted owner settings — the AI ceiling, the asset-cache policy and its limits, and the emergency switch, polled
    and applied without a restart ([SERVER_SETTINGS.md](../SERVER_SETTINGS.md)).
  - the public room directory — a `directoryId` on every room, `lobby.watch` / `lobby.join` / `lobby.spectate` over the
    compact wire, and `room.setMatchmaking`; a stale directory summary grants no admission.
- **Compatibility note:** `public/js/assetCache.js` now carries both 0.3.1's browser asset *import* helpers and the
  asset-cache *manager* (`createAssetCacheManager`, `assetCache`) — the two upstream files shared a name and had no
  export in common.
- **Tests:** `test/lobby-access.test.js`, `lobby-discovery`, `plugins-client`, `announcement-assets-http`,
  `announcement-notices-*`, `announcements-*`, `asset-cache-*`, `bandwidth-emergency` and `server-settings`.
