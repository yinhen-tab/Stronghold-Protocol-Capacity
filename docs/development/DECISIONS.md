# 已确认的分支决定

本文件记录用户已确认并影响后续维护的规则。编号固定，状态为「生效」或「被替代」；规则变更时新增决定并互相链接，保留旧理由。回溯整理日期为 2026-10-08，历史提交与任务记录是实现依据。

## D001

**生效：房间硬上限 20，默认 8，按实际参战人数适配。**

- 房间可选 4 / 8 / 10 / 16 / 20；空位、观战者不作为参战玩家。独立模拟保持单人。
- 原因：先实现至少 8 人，并保留 10、16、20 人的扩展能力；不能因开了大房而让少量玩家承担满房内容。
- 依据：[容量记录](records/2026-10-06-01-player-capacity.md)，`e32edbb`、`309c7a1`；当前规则见 [PLAYER_CAPACITY.md](../PLAYER_CAPACITY.md)。

## D002

**被替代：旧机变按全房存活人数扩容，现由 [D012](#d012) 的每组独立六张维护。**

- 数量为 `min(22, max(6, 存活人数 + 2))`。扩容悬赏保留原六张的分布，再洗牌复制；重复卡片是独立位置。
- 原因：人数增加后仍有选择空间，且不会让四人进入大房时也看到满房选项。
- 第三次机变不强制改为装备/支援，沿用当前上游的类型生成；v0.2.1 同步已核对回合规则，玩家对缺席的怀疑仍属于 I001 待复现。
- 依据：[容量记录](records/2026-10-06-01-player-capacity.md)、[反馈调查](records/2026-10-07-03-playtest-feedback.md)；实现入口 [choices.js](../../server/match/choices.js)。
- 替代：2026-10-08 用户认为扩容复制过多、全房串行太慢，改为固定卡池组并行、各组六张独立生成；允许跨组偶然整套相同。原机变回合及类型概率继续保留，I001 不因这次改造记为已修复。

## D003

**被替代：旧大房分组卡池，现由 [D010](#d010) 维护；三人组完整原池继续保留。**

- 1–4 人保持原池；5/6 人用 1.25/1.5 倍，副本向上取整；≥7 人按开局座位分成尽量均衡、最多四人的组。
- 7=4+3、8=4+4、10=4+3+3；三人组不缩到 0.75 倍。这是用户对最初「各组按人数÷4」方案的明确修正。
- 分组不随淘汰重新分配；返还副本留在所属组。信标跨组赠送从接收者组取得副本，保持原延迟赠送机制。
- 原因：避免所有人挤在巨大的单池里，也避免三人组副本过少。
- 依据：[容量记录](records/2026-10-06-01-player-capacity.md)；实现入口 [pool.js](../../server/match/pool.js)、[playerCapacity.js](../../shared/playerCapacity.js)。
- 替代：2026-10-08 用户要求取消六人池，并指定含五人组的新分组表及五人 III 阶 22；见 D010。上述六人池及旧九人分组只属于历史方案。

## D004

**生效：开局策略和所有机变，每个固定卡池组内手动人类玩家先选。**

- 在线且未托管的真人先于本组 AI、托管和掉线席位；两个优先类别内部保持随机顺序，连接/托管变化只重排所在组未选席位。组间不等待其他组的真人，见 [D012](#d012)。
- 策略「跳过」排到本组其他手动真人之后、自动席位之前，不让本组 AI 趁跳过占先。
- 机变时限按开局真人数判断：仅一位真人可带 AI 且不限时；多真人房保留超时自动选择。不能把单真人房挂机当作自动选择的确定原因。
- 原因：先保证能操作的人的选择权，再快速处理自动席位。
- v0.2.2 合并延续本决定：上游可关闭的 AI 后选开关在本分支显示为固定启用；兼容开启请求，拒绝关闭请求，不增加托管/掉线真人相对 AI 的第三层排序。见 [合并记录](records/2026-10-09-03-upstream-v0.2.2.md)。
- 依据：[轮选记录](records/2026-10-07-02-manual-drafts.md)，`1422876`；实现入口 [Match.js](../../server/match/Match.js) 的 `prioritizeDraftOrder`。

## D005

**被替代：旧领袖血量基准与机制扣血约定，现由 [D009](#d009) 维护。**

- 同盟血池按原值 × 存活人数 / 4；人数变化保留血量百分比，独立模拟保持原 0.25 倍。
- 胄的死亡集群无人机被击杀时仍扣共享最大血量的 2%，该项机制扣血豁免 300000 限伤；普通攻击、元素伤害及部件传递保留原有限伤。
- 原因：扩容后百分比机制可能超过普通攻击上限；只修正该机制，不把所有攻击的限伤一起取消。
- 依据：[反馈修复](records/2026-10-07-03-playtest-feedback.md)，`0a1fe03`；实现入口 [Battle.js](../../server/sim/Battle.js)、[bosses.js](../../server/sim/content/bosses.js)。
- 替代：2026-10-08 合并 v0.2.1 时，用户改为采用上游完整的每人血量基准，仍保留退出时百分比缩血及无人机机制豁免；见 D009，旧规则和理由保留供追溯。

## D006

**被替代：旧八人两轮联防及首轮投票，现由 [D013](#d013) 的固定组数轮次和逐轮投票维护。**

- 每轮最多两位不同的完美作战队友，一回合最多四位。首轮仍漏怪且有后续合格队友才进入第二轮。
- 仅计划两轮且首轮作战期间提供投票。未离开、在线、未托管的真人有资格，包含已淘汰者；观战、AI、掉线和托管不计入。
- 门槛为 `floor(有资格人数 / 2) + 1`；资格变化移除失效票并重算。通过后不撤销，首轮继续结束，再按剩余漏怪结算，保留收益和统计。
- 原因：人数多时漏怪可能过量，避免无胜算的第二轮拖慢进度，同时把决定权交给仍能参与的人。
- 依据：[反馈修复](records/2026-10-07-03-playtest-feedback.md)，`8fbac6d`；实现入口 [unite.js](../../server/match/unite.js)、[Match.js](../../server/match/Match.js)。
- 替代：2026-10-08 用户要求联防轮数上限等于固定组数，并确认每轮可投票、当前轮打完后取消本回合后续全部联防；原资格、严格过半、通过锁定及最终漏怪结算边界由 D013 保留。

## D012

**生效：策略和机变按固定卡池组并行轮选，机变各组独立六张。**

- 使用 D010 的开局固定分组，组内依次轮选、组间同时开始；每组拥有独立进度和计时，所有组完成后进入下一阶段。淘汰和退出不重分组；没有存活成员的组不生成奖励页、不阻塞阶段。
- 开局策略只在同组内禁止重复，跨组可重复。其他组已选策略在卡片右侧显示对应 A–E 色标，轮选成员列表复用 D011 角标和淡框；保留原头像、生命值塔图标及本组已选头像。
- 每次机变全房抽一次事件类型，沿用上游回合和类型概率；各个仍有参选者的组完全独立生成六张，保留悬赏原组合与强弱规则、装备和战术原有重复位置。单卡及整套跨组偶然相同均允许，不额外重抽或去重。独立模拟仍三选，训练的既有六选例外保留。
- 默认打开本组页，其他组可只读查看选项、选择进度和倒计时。切页清除待确认卡；新机变或本组轮到自己时返回本组，自己正在选择时仍可主动浏览别组。淘汰玩家保留本组只读页，观战初始显示首个未完成组。
- 每组内沿用 D004 真人优先、跳过、托管和连接状态规则。策略每轮 30 秒，机变本组首轮 30 秒、后续 16 秒；开局仅一名人类的房间仍不限时。别组选卡不重置本组时钟。
- 带全队标记的盟誓、财富、补给等支援继续覆盖全房存活队友，可能叠加多次收益；用户已明确选择保留这一范围。信标仍可跨组发送，副本从接收者组获得，私人自选库存边界不变。
- 新客户端提交阶段标识和组编号，服务端按玩家所属组验证；省略标识的旧请求仍可兼容。多人阶段的公开总倒计时不作为某组时钟，客户端读取本组或所查看页的计时。
- 原因：降低二十人串行等待和复制选项的重复感，让分组成为后续玩法和界面的稳定单位；本次不将战场联防或领袖搭档改为固定组。
- 依据：[本次并行轮选记录](records/2026-10-08-05-parallel-group-drafts.md)；实现入口 [phases.js](../../server/match/match/phases.js)、[spDraft.js](../../server/match/match/spDraft.js)、[choices.js](../../server/match/choices.js)、[bandDraft.js](../../public/js/screens/bandDraft.js)、[choiceOverlay.js](../../public/js/ui/choiceOverlay.js)。替代 D002 的全房扩容，补充 D004 的组内优先边界。

## D013

**生效：联防轮数上限为开局固定组数，每轮可投票在本轮结束后跳过后续全部联防。**

- D010 的固定组数对应一至五轮上限：1–5 人一轮、6–9 人两轮、10–13 人三轮、14–17 人四轮、18–20 人五轮。人数是开局实际参战数；退出、淘汰或空组不会重算这个上限。合格队友不足时实际计划缩短，无剩余漏怪或可用候补时提前结算。
- 每轮仍最多两人，全回合最多十名不同助手；从全房完美作战队友中沿用原排序选人，固定组只提供轮数上限。当前源码按场上干员数、有效羁绊、站立干员及座位选，再对每对按层数细排，不改为随机或每组固定派人。后续保留候补并过滤已用、退出和淘汰者。
- 联防严格逐轮执行，保留原轮间收尾、存活漏怪属性/来源/悬赏、干员 HP/SP 携带和各轮收益/统计。只有最后剩余漏怪扣原来源玩家 LP，仍用每回合扣血上限；通过投票不强制结束当前战斗。
- 当前轮有后续计划和合格候补时提供「投票跳过后续全部联防」。每轮票数重置，资格为未离开、在线、未托管的真人，包含已淘汰者；AI 和观战者不计入。门槛仍为 `floor(有资格人数 / 2) + 1`，失去资格移除票并重算，零人不自动通过。通过后锁定，本轮正常结束，再取消本回合后续全部联防并结算。
- 新客户端请求携带当前轮 voteId，过期轮次或其他回合的投票标识被拒绝；旧无标识请求兼容。最后一轮或候补耗尽时不显示投票。HUD 显示当前/计划轮次，例如 3/5，按钮、提示与通过消息均明确「后续全部联防」。
- 原因：二十人房两轮可能不足，利用更多合格队友，同时允许多数真人缩短无胜算的后续流程。用户担心即时切轮压力；选择正常结束后取消全部后续，沿用当前生命周期，避免直接中断带来的旧浏览器战斗和漏怪收尾问题。真实带宽峰值尚未测量，不据源码推断宣称性能已验证。
- 依据：[本次联防记录](records/2026-10-08-06-group-unite-rounds.md)；实现入口 [playerCapacity.js](../../shared/playerCapacity.js)、[unite.js](../../server/match/unite.js)、[unitePhase.js](../../server/match/match/unitePhase.js)、[hud.js](../../public/js/ui/hud.js)。替代 D006，保留其投票资格、多数规则和结算边界。

## D014

**生效：公告采用服务器本地 Markdown 与终端发布，普通提醒按新发布版本重置。**

- 无账号、数据库或网页发布后台；服主 CLI 写入私有公告目录，公开接口仅可读取。历史标题列表和正文独立滚动，默认选置顶或最新，最多一条置顶。
- 有公告时进入网站自动显示，无置顶也显示；「下次不再显示」绑定当前总体发布版本，没有日期期限，下一次发布使其失效。置顶变化不算发布；手动按钮忽略免提示。空安装不自动显示空弹窗。
- 原始 HTML 只显示文字，常用 Markdown 子集由已有 Preact 安全渲染，不加载外部编辑器或数据库。初版图片显示文字的限制由 [D015](#d015) 取消；公告运行数据不提交 Git。
- 公告正文允许原生文字选中复制；标准 Markdown 链接、直接粘贴的 HTTP/HTTPS 网址及尖括号网址可点击，在新标签页打开，保留分享参数并隔离 opener。代码与原始 HTML 中的网址仍为文字；这是链接访问能力，不解除 D015 的外链图片限制。见 [网址与复制修复](records/2026-10-10-04-announcement-links-copy.md)。
- 普通发布不自动弹到正在游玩的玩家，也不挡断线恢复。局内紧急弹窗仅允许服主显式 `notify <公告ID>` 命令触发，独立于发布及普通免提示；按用户要求另交一个功能提交。向全体在线连接发送引用，包含观战者和未输入代号的连接；不暂停游戏、不退出或刷新对局。
- 紧急通知不显示免提示，独立队列依次阅读，命令及未显示队列项有效期为五分钟；已显示通知留到玩家关闭。启动跳过旧命令，不给断线者补发，不将命令写入成功当作阅读确认。
- 原因：用户原拟用账号兼顾断线恢复，讨论多机部署和部署成本后取消账密计划；明确选择简单文件公告，以及持续到新公告发布的免提示方式。
- 依据：[本次公告记录](records/2026-10-09-01-announcements.md)、[使用说明](../ANNOUNCEMENTS.md)；实现入口 `server/announcements.js`、`tools/announcements.mjs`、`public/js/ui/announcementModel.js`。

## D016

**生效：统一完整素材 ZIP 优先本地导入，在线只按内容哈希补缺，默认总预算 8 Mbps。**

- 服主从实际安装的素材与配套清单生成统一包，包含字体、语音及本地补充模型；导入只在玩家本机处理。旧包和部分包中仍匹配当前 SHA-256 的文件可复用，中断接续以完整文件为单位。更新时按文件哈希判断，不因应用版本号变化重下全部素材。
- HTTPS/localhost 的现代浏览器使用 Service Worker 与 Cache Storage；不支持时按原方式加载。只缓存 assets、fonts 及清单内的 media 别名；网页、代码、游戏数据、公告和 WebSocket 不纳入。配额及持久保存遵循浏览器实际结果，不能承诺永久保存或完全离线游戏。
- 入口保留在大厅及房间导航，使用明显的背景框；标题页不提供预缓存入口。本地导入明确标注「强烈推荐」；持久保存申请需显示处理中、浏览器允许/未授予/不支持/异常的实际结果，不能仅静默调用 API。见 [界面反馈修复](records/2026-10-09-06-asset-cache-ui.md)。
- 单 Node.js 进程默认补齐总预算为 1000000 B/s（8 Mbps），同网络 IP 上限为 500000 B/s（4 Mbps），按活跃客户端轮转；环境变量可调整或禁用。限速仅约束在线补齐接口，普通游戏请求不排队；不探测或自动追随云服务器标称出口。2026-10-10 用户根据单人下载速度将原 1 Mbps 上限提高到 4 Mbps，总预算不变；见 [速率调整记录](records/2026-10-10-02-asset-cache-ip-limit.md)。
- 批量导入、下载、深度校验和清理共享跨标签页互斥。任一同站点标签页进入对局时暂停批量任务；返回大厅后手动继续。各页面固定素材清单版本，正在使用的旧版本不被增量更新删除；未固定版本的新页面先使用正常网络。
- 服务端清单在进程内固定，补充素材后需重启；完整性与内容版本分别报告。完整包不进 Git，发布与服务器部署仍需独立授权。可人工从网盘或独立静态站分发 ZIP，本功能不自动上传外部平台。
- 原因：用户要求优先减轻素材请求带宽，确认完整包统一分发、本地导入优先、增量更新，并选择 8 Mbps 初始预算；近百人生产压力和云链路骤降效果仍需部署环境验证。
- 依据：[本次实现记录](records/2026-10-09-05-asset-precache.md)、[玩家与服主说明](../ASSET_CACHE.md)；入口 `server/assetCacheCatalog.js`、`server/http/assetCache.js`、`public/js/assetCache.js`、`public/asset-cache-sw.js`、`tools/asset-cache-pack.mjs`。
